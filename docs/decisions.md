# บันทึกการตัดสินใจ (Decision Log)

สรุปสิ่งที่ตกลงกันไว้ก่อนเริ่มเขียนโค้ด พร้อมเหตุผล — เพื่อให้ทุกคนในทีม
(และตัวเราเองตอนเหนื่อยชั่วโมงที่ 10) ไม่ต้องถกเรื่องเดิมซ้ำ

---

## 1. เทคโนโลยี: Next.js + FastAPI + PostgreSQL

โจทย์ข้อ 10 ระบุชื่อทั้งสามตัวไว้ตรง ๆ ในรายการที่อนุญาต จึงไม่ต้องขออนุญาตเพิ่ม

**ข้อได้เปรียบที่ตั้งใจใช้:** FastAPI สร้าง OpenAPI + Swagger UI ที่ `/docs` ให้อัตโนมัติจาก
Pydantic models → ได้ deliverable ข้อ "เอกสาร API พร้อมตัวอย่าง request/response" แทบไม่ต้องลงแรง
และเปิดหน้านี้โชว์กรรมการตอนนำเสนอได้เลย

**ข้อควรระวัง:** อย่าเขียน business logic ใน Next.js API routes เพราะโจทย์ให้คะแนนการแยก FE/BE
ชัดเจน ถ้ากฎจำแนกประเภทไปโผล่ฝั่ง Next.js กรรมการจะถามว่าตกลงใครเป็น backend

## 2. ไม่ใช้ Docker

เดิมตั้งใจใช้ Docker Compose แต่เปลี่ยนเมื่อรู้ว่าทีมใช้เครื่องเดียว —
**ประโยชน์หลักของ Docker คือทำให้ทุกเครื่องเหมือนกัน ซึ่งไม่มีความหมายเมื่อมีเครื่องเดียว**
เหลือแต่ต้นทุน: กิน RAM, ต้องดาวน์โหลดหลาย GB, rebuild ทุกครั้งที่แก้ dependency

ตอนนี้ย้ายมา WSL ที่มี PostgreSQL 14 รันอยู่แล้ว ยิ่งไม่จำเป็น

## 3. Python 3.13 ผ่าน uv (ไม่ใช้ python3 ของระบบ)

Ubuntu 22.04 มาพร้อม Python 3.10 ซึ่งไม่มี `StrEnum` (3.11+) และ `datetime.UTC` (3.11+)
ทางเลือกคือเขียนโค้ดให้เข้ากับ 3.10 หรือดึง 3.13 มาแยก — เลือกอย่างหลัง เพราะ `uv python install`
ใช้เวลาไม่กี่วินาที ไม่ต้อง sudo และไม่กระทบ `python3` ของระบบที่ใช้กับงานอื่นอยู่

## 4. Node 24 ผ่าน nvm

เครื่องตั้ง nvm default ไว้ที่ Node 12 และ shell ปกติได้ Node 16 — ทั้งคู่รัน Next.js 16 ไม่ได้
โชคดีที่มี Node 24.14.1 ติดตั้งไว้อยู่แล้ว จึงเพิ่ม `.nvmrc` ระบุ `24` ให้ทุกคนใช้เวอร์ชันเดียวกัน

## 5. วิธีทำงาน 3 คน 1 คีย์บอร์ด

โจทย์มี deliverable 6 ชิ้น แต่**มีแค่ชิ้นที่ 4 (Working Software) ที่ต้องใช้เครื่อง**
อีก 5 ชิ้นทำบนกระดาษได้ (โจทย์ระบุเองว่า wireframe "จะเป็นภาพร่างหรือไฟล์ออกแบบก็ได้")

| ตำแหน่ง | ทำอะไร |
|---|---|
| Driver | จับคีย์บอร์ด เขียนโค้ด |
| Navigator | อ่านโจทย์เทียบ จับ bug เปิด Swagger เช็ก API ไล่ test case |
| Scribe | เอกสาร: requirement, use case, ER, wireframe, test case, สไลด์ |

**สลับทุก 90 นาที** → ทุกคนได้ drive จริง ได้ทำเอกสารจริง และอธิบายส่วนที่ตัวเองรับผิดชอบได้
ตอนนำเสนอ ซึ่งเป็นเกณฑ์ข้อ 4 (20 คะแนน) ตรง ๆ

ผลพลอยได้: pair programming ทำให้ไม่มี merge conflict เลย ซึ่งทีมที่ใช้ 3 เครื่องมักเสียเวลา 1–2 ชม.

## 6. Git: ระบุ author ตามคนที่ drive

ถ้า commit ปกติ ทุก commit จะขึ้นชื่อเจ้าของเครื่องคนเดียว กรรมการเปิด repo แล้วจะเห็นว่า
มีคนทำคนเดียว → เสียคะแนนข้อ "สมาชิกทุกคนมีส่วนร่วมในการพัฒนา" ทั้งที่ทุกคนทำจริง

แก้ด้วย `./scripts/git-setup.sh` ที่สร้าง alias:

```bash
git ca a -m "feat: ..."   # commit ในชื่อสมาชิก A
git who                   # ดูว่าแต่ละคน commit ไปกี่ครั้ง
```

เปิด `git who` หรือหน้า Contributors บน GitHub โชว์กรรมการได้ตอนนำเสนอ

## 7. ระบบดีไซน์

ค่าสีดึงจากไฟล์โลโก้จริง ไม่ได้กะเอาจากภาพ:

| | Hex | ใช้ที่ |
|---|---|---|
| Teal | `#009494` | ปุ่มหลัก, active, แบรนด์ |
| Teal สว่าง | `#00A6A6` | hover |
| Navy | `#0D2344` | ตัวอักษรหลัก, เส้นขอบ |
| Mint | `#C8EDE2` | พื้นอ่อน, badge |

**ลายเซ็นของสไตล์นี้ที่ต้องไม่ทำหาย** (ดูตัวอย่างใน `docs/reference-ui/`):

1. **หัวข้อเป็นคำถามที่พูดกับผู้ใช้** — "ที่พักของคุณต้องดำเนินการอะไร?" ไม่ใช่ "แบบฟอร์มประเมินประเภทที่พัก"
2. **ทุกหัวข้อมีคำอธิบายสั้นใต้ชื่อเสมอ** ไม่มี label ลอย
3. **รหัสเอกสารนำหน้าเสมอ** — A01–A08 (ทำเองได้) / B01–B07 (ต้องขอจากหน่วยงานอื่น)
4. **Layout 2 คอลัมน์ 60/40** — ซ้าย = สิ่งที่ต้องทำ, ขวา = บริบท/ผลลัพธ์/ความช่วยเหลือ
5. **Badge "ต้นแบบ • ข้อมูลจำลอง" ข้างโลโก้** + footer disclaimer — ตอบกติกาข้อห้ามใช้ข้อมูลจริงไปในตัว
6. ภาพประกอบลายเส้นและข้อความลายมือมุมล่างซ้าย

## 8. มาสคอต — แมปท่าทางกับสถานะ ไม่ใช่เลือกตามความสวย

| ท่า | ใช้ที่ |
|---|---|
| `wave` | หน้าแรก, ต้อนรับหลังสมัคร, empty state ทั่วไป |
| `upload` | dropzone ว่าง, ระหว่างอัปโหลด (M5) |
| `inspect` | AI ช่วยตรวจ (S1), เจ้าหน้าที่กำลังตรวจ (M8), ผลค้นหาว่าง |
| `waiting` | รอดำเนินการ, "อยู่ในขั้นนี้ N วัน" (M7), คำขอค้าง |
| `success` | ยื่นสำเร็จ (M6), อนุมัติ, ใบอนุญาต (M10) |
| `support` | ช่วยเหลือ, FAQ, กระดานสนทนา (C1), หน้า error |

**หลักที่ถือไว้: อย่าให้มาสคอตยิ้มร่าเริงตอนบอกข่าวร้าย** — ตอนแจ้ง "ไม่ผ่าน" ให้ใช้ไอคอนธรรมดา
จะดูน่าเชื่อถือกว่า และมาสคอตต้องไม่เป็นตัวสื่อความหมายเพียงลำพัง ต้องมีข้อความกำกับเสมอ (NFR Accessibility)

**ท่าที่ยังขาดและควรเจนเพิ่ม:** ท่า "เอกสารขอให้แก้ไข" (เอียงคอ ทำหน้างง ไม่ใช่หน้าเศร้า)
สำหรับ T-08 ซึ่งเป็น flow ที่ต้องเดโมแน่นอน

## 12. ลายมือชื่อในแบบฟอร์ม และการออกเป็น PDF

ระบบมีแบบฟอร์มที่กรอกให้เองได้ทั้งฉบับสองแบบ แยกตามผลจำแนกประเภท:
**A01 แบบหนังสือแจ้งสถานที่พักที่ไม่เป็นโรงแรม** (เส้นไม่เข้าข่ายโรงแรม) และ
**A06 แบบ ร.ร.1 คำขอรับใบอนุญาตประกอบธุรกิจโรงแรม** (ประเภทที่ 1 และ 2)
ทั้งคู่ระบบกรอกให้ได้หมดยกเว้นสิ่งเดียวคือ **ลายมือชื่อผู้ยื่น** ซึ่งเป็นสิ่งที่
ทำให้เอกสารฉบับนั้นมีผล จึงต้องมีทั้งช่องให้ลงลายมือชื่อในระบบ และทางออกเป็นไฟล์
ที่พิมพ์/ส่งต่อได้

ทั้งสองฉบับใช้ endpoint เดียว (`GET /applications/{no}/forms/{code}`) service เดียว
(`services/system_form.py`) และโครงกระดาษเดียว (`SystemFormPaper.tsx`) ต่างกันแค่
เนื้อความตรงกลาง ถ้าทำเป็นสองชุดคู่ขนาน สองชุดนั้นจะค่อย ๆ เพี้ยนจากกัน
แบบเดียวกับที่ `api/presenters.py` มีไว้กันไม่ให้ /wizard กับ /applications เพี้ยนกัน

**PDF: ใช้การพิมพ์ของเบราว์เซอร์ ไม่สร้างไฟล์ฝั่งเซิร์ฟเวอร์**
เหตุผลเดียวกับใบอนุญาต (M10) — หน้าต่างพิมพ์ของทุกเบราว์เซอร์มีปลายทาง
"บันทึกเป็น PDF" อยู่แล้ว การเพิ่มไลบรารี PDF ฝั่ง Python แลกมาด้วยปัญหา
ฟอนต์ไทย (สระบนล่างเพี้ยน ต้องฝังไฟล์ฟอนต์เอง) ซึ่งกินเวลามากเกินกว่าที่มี
และได้ผลลัพธ์ที่แย่กว่า หน้าเว็บจึงเป็นทั้งหน้าจอและต้นฉบับกระดาษในตัวเดียวกัน

**ลายมือชื่อเก็บเป็นไฟล์แนบของ A01 ไม่ใช่คอลัมน์ใหม่**
ทางเลือกคือเพิ่ม `signature_path` ใน `application` หรือใช้กลไกเอกสารที่มีอยู่
เลือกอย่างหลัง เพราะได้มาฟรีทั้งชุด: เซ็นใหม่กลายเป็นรุ่นถัดไปโดยไม่ทับของเดิม
(ข้อ 8 ของโจทย์) เจ้าหน้าที่ตรวจและขอให้แก้ไขได้เหมือนเอกสารฉบับอื่น
และล็อกอัตโนมัติเมื่อยื่นคำขอแล้ว โดยไม่ต้องเขียนกฎเพิ่มสักบรรทัด

**ต้องลงลายมือชื่อก่อนจึงจะยื่นได้ (มติทีม)**
แบบฟอร์มในระบบไม่ถูกยกเว้นใน `missing_mandatory` อีกต่อไป เพราะลายมือชื่อคือ
สิ่งที่ทำให้หนังสือแจ้งมีผล การปล่อยให้ยื่นหนังสือที่ไม่มีลายมือชื่อได้เท่ากับ
ระบบยอมรับเอกสารที่ใช้ไม่ได้จริง ผลที่ตามมาสามอย่างซึ่งตั้งใจให้สอดคล้องกัน:

1. `missing_mandatory` นับแบบฟอร์มที่ยังไม่เซ็นเป็นเอกสารที่ขาด และติดธง
   `needs_signature` มาด้วย เพื่อให้ข้อความบอกว่า "ยังไม่ได้ลงลายมือชื่อ"
   ไม่ใช่ "ยังไม่ได้แนบไฟล์" ซึ่งจะพาผู้ใช้ไปหาไฟล์มาแนบผิด ๆ
2. สถานะของแบบฟอร์มที่ยังไม่เซ็นเป็น "ยังไม่ได้อัปโหลด" ไม่ใช่ "อัปโหลดแล้ว"
   ไม่งั้นสถานะจะขัดกับปุ่มยื่นที่กดไม่ได้ และผู้ใช้จะหาไม่เจอว่าติดตรงไหน
3. ลายมือชื่อถูกนับใน `pending_documents` ของเจ้าหน้าที่ด้วย ไม่งั้นมันจะเป็น
   สิ่งเดียวในคำขอที่ไม่มีใครตรวจ

ผู้ที่ถนัดเซ็นบนกระดาษยังทำได้เหมือนเดิม — พิมพ์แบบฟอร์มออกไปเซ็น ถ่ายรูป
แล้วอัปโหลดรูปนั้นกลับเข้ามา ระบบจึงไม่ได้ปิดทางใคร

**ช่องติ๊กเอกสารแนบในแบบ ร.ร.1 ไม่ได้เก็บเป็นข้อมูล**
แบบ ร.ร.1 มีช่องให้ติ๊กว่าแนบเอกสารใดมาด้วย (A07–A09) ระบบติ๊กให้เองจากว่า
แนบไฟล์แล้วหรือยัง ไม่ได้เพิ่มคอลัมน์ "ติ๊กแล้ว" เพราะนั่นคือข้อมูลชุดเดียวกัน
ที่เก็บซ้ำสองที่ (3NF) และจะเพี้ยนทันทีที่มีคนติ๊กแต่ไม่แนบ หรือแนบแต่ไม่ติ๊ก

**ชื่อผู้ยื่นบนแบบฟอร์มแก้ได้เอง**
แบบ ร.ร.1 มีช่องบุคคลธรรมดา/นิติบุคคล แต่ตอนสมัครระบบตั้งชื่อผู้ประกอบการให้
เท่ากับชื่อ-นามสกุลของผู้สมัครไปก่อน จึงเพิ่ม `PATCH /applications/{no}/applicant`
ให้แก้ได้ตราบที่คำขอยังไม่ถูกยื่น แก้ที่ตาราง `operator` ไม่ใช่ `app_user`
เพราะ "ผู้ประกอบการ" กับ "บัญชีผู้ใช้" เป็นคนละสิ่ง (ดูคอมเมนต์ใน models/property.py)
เลขทะเบียนนิติบุคคลเก็บเป็นตัวเลขล้วน 13 หลักด้วยเหตุผลเดียวกับเบอร์โทร

## 13. ลายมือชื่อผู้ลงนามบนเอกสารที่ระบบออกให้ (M10)

ใบอนุญาตและหนังสือรับรองการแจ้งเดิมมีแต่ชื่อเจ้าหน้าที่เป็นข้อความ ซึ่งยังไม่ใช่
เอกสารที่ลงนามแล้ว ด้วยเหตุผลเดียวกับข้อ 12 จึงให้เจ้าหน้าที่ลงลายมือชื่อ
**ตอนกดออกเอกสาร** และลายมือชื่อนั้นไปปรากฏบนกระดาษที่ผู้ยื่นพิมพ์ออกไป

**การเซ็นคือขั้นตอนเดียวกับการออกเอกสาร ไม่ใช่ขั้นตอนแยก** — ปุ่ม "ออกใบอนุญาต"
กลายเป็นปุ่ม "ลงนามและออกเอกสาร" ใต้ช่องเซ็น ถ้าแยกเป็นสองปุ่มจะเกิดสถานะกลางที่
เอกสารออกไปแล้วแต่ยังไม่มีใครลงนาม ซึ่งเป็นสถานะที่ไม่ควรมีอยู่จริง

**เก็บเป็นไฟล์ ไม่ใช่ document_file** — ตาราง `document_file` ผูกกับ "เอกสารประกอบ
คำขอ" ที่ต้องมี `document_type` และเข้าสู่กระบวนการตรวจของเจ้าหน้าที่
ลายมือชื่อผู้ลงนามเป็นส่วนหนึ่งของเอกสารที่ระบบออก ไม่ใช่ของที่ผู้ยื่นส่งมาให้ตรวจ
จึงเก็บเป็น `license.issuer_signature_path` (migration `5b1e70c4a9d2`)
เก็บเป็น path ไม่ใช่ไบต์ในฐานข้อมูล ด้วยเหตุผลเดียวกับ `document_file.stored_path`

ใบที่ออกไปก่อนหน้านี้ไม่มีลายมือชื่อเก็บไว้ หน้าพิมพ์จึงเว้นเส้นลงชื่อไว้ให้เซ็น
ด้วยปากกา แทนที่จะพังหรือขึ้นรูปว่าง

**ทางเลือกสองทางในการเซ็น** — วาดบนจอ หรืออัปโหลดรูปลายเซ็น — ไม่ใช่ของแถม
แต่จำเป็นตาม NFR Accessibility เพราะผู้ที่ใช้คีย์บอร์ดอย่างเดียววาดด้วยเมาส์ไม่ได้
ทั้งสองทางออกมาเป็น PNG พื้นหลังโปร่งเหมือนกัน เพื่อให้วางทับเส้นลงชื่อได้ไม่บังเส้น

## 14. แชทบอทผู้ช่วยตอบคำถาม — ยังไม่ต่อ AI โดยตั้งใจ

คำถามที่ผู้ประกอบการถามเจ้าหน้าที่ซ้ำ ๆ มีอยู่ไม่กี่กลุ่ม: ขั้นตอนเป็นอย่างไร
ต้องเตรียมเอกสารอะไร และคำขอของฉันถึงไหนแล้ว ทั้งสามกลุ่มนี้ระบบมีคำตอบอยู่แล้ว
ในฐานข้อมูล แค่ยังไม่มีทางถามที่เร็วกว่าการไล่หาเองในหน้าจอ

**ทำเป็นชุดคำถามที่เตรียมไว้ + จับคำสำคัญ ไม่ต่อโมเดลภาษา** เหตุผล:

1. ทีมต้องอธิบายโค้ดทุกบรรทัดที่ส่งได้ (โจทย์ข้อ 10) คำตอบที่มาจากโมเดล
   อธิบายไม่ได้ว่าทำไมถึงตอบแบบนั้น และซ้อมเดโมให้ได้ผลเดิมทุกครั้งไม่ได้
2. เกณฑ์ข้อ 3 ให้คะแนน "ใช้งานได้จริงตอนเดโม" การเรียก API ภายนอกกลางเวทีคือ
   จุดพังที่ควบคุมไม่ได้ ทั้งเรื่องเน็ต คีย์ และเวลาตอบ
3. ของจริงที่ผู้ใช้ต้องการคือ "คำตอบที่ถูก" ไม่ใช่ "ภาษาที่ลื่น" ซึ่งชุดคำถาม
   ที่เตรียมไว้ทำได้ครบอยู่แล้ว

**คำตอบที่เกี่ยวกับกฎเกณฑ์ต้องดึงจาก API เสมอ ห้ามเขียนไว้ในแชทบอท**
รายการเอกสาร ชนิดไฟล์ที่รับ ขนาดไฟล์สูงสุด ค่าธรรมเนียม จำนวน อปท. และสถานะคำขอ
ทั้งหมดมาจาก endpoint จริง เพราะ Super Admin แก้ค่าเหล่านี้ได้เอง (US-09)
ถ้าเขียนตัวเลขไว้ในคำตอบ วันที่กฎเปลี่ยนแชทบอทจะกลายเป็นตัวให้ข้อมูลผิด
ซึ่งแย่กว่าไม่มีแชทบอทเลย — เช่น คำถาม "ต้องเตรียมเอกสารอะไรบ้าง" บอทถามขนาด
ที่พักแล้วยิง `/wizard/classify` จริง ไม่ได้เก็บเกณฑ์ห้อง/คนไว้ในตัวเอง

**ตอบเรื่องคำขอของตัวเองได้** เป็นกลุ่มที่ลดภาระเจ้าหน้าที่ได้มากที่สุด บอทอ่าน
สถานะจริงผ่าน API ที่กรองด้วยเจ้าของคำขออยู่แล้ว จึงไม่มีทางเห็นคำขอของคนอื่น
และใช้ตารางแปลงสถานะชุดเดียวกับหน้าจอ (`lib/progress.ts`) คำตอบจึงตรงกับที่
เห็นบนหน้าคำขอเสมอ

**สิ่งที่เพิ่มฝั่ง API เพราะแชทบอทเปิดช่องโหว่ให้เห็น:** `decision_reason` เดิม
ส่งให้เฉพาะฝั่งเจ้าหน้าที่ ผู้ยื่นจึงรู้แค่ว่า "ถูกตีกลับ" แต่ไม่รู้ว่าต้องแก้อะไร
และ `max_upload_mb` เดิมอยู่แต่ในเซิร์ฟเวอร์ หน้าจอไม่มีทางรู้โดยไม่เดา
ทั้งสองค่าถูกส่งออกมาแล้ว

## 15. อีเมลแจ้งเตือนผู้ยื่นเมื่อเจ้าหน้าที่ตัดสิน

ปัญหาที่แก้: เดิมผู้ยื่นรู้ผลก็ต่อเมื่อเปิดเว็บมาดูเอง คนที่ถูกตีกลับอาจค้าง
หลายวันโดยไม่รู้ตัว แล้วจบลงที่การโทรถามเจ้าหน้าที่ ซึ่งเป็นภาระที่โจทย์อยากลด
ส่งไปยังอีเมลที่ใช้สมัครสมาชิก (M1)

**ส่งเฉพาะตอนเจ้าหน้าที่ลงมือ** — ขอให้แก้ไข / อนุมัติ / ไม่อนุมัติ / ออกเอกสาร
ไม่ส่งตอนผู้ยื่นทำอะไรเอง เพราะเขารู้อยู่แล้วว่าเพิ่งกดอะไรไป การส่งทุกเหตุการณ์
จะกลายเป็นอีเมลขยะที่คนเลิกอ่าน แล้วพลาดฉบับที่สำคัญจริง

**ส่งหลัง commit และนอก request (BackgroundTasks)** เพราะการส่งเมลต้องไม่มีสิทธิ์
ทำให้ผลการพิจารณาที่บันทึกแล้วล้มเหลว ถ้าเซิร์ฟเวอร์เมลล่มหรือช้า เจ้าหน้าที่
ต้องยังกดอนุมัติได้ตามปกติ ฟังก์ชันแจ้งเตือนจึงกลืน exception ทุกชนิด
แล้วบันทึกผลลง AuditLog แทน ทั้ง success / failed / skipped — มีเทสต์
`test_sending_failure_never_breaks_the_decision` คุมไว้

**สองช่องทาง เลือกด้วย `EMAIL_BACKEND`**

| ค่า | พฤติกรรม | ใช้เมื่อ |
|---|---|---|
| `outbox` (ค่าเริ่มต้น) | เขียนไฟล์ลง `storage/outbox/` | พัฒนาและสาธิต — เปิดไฟล์ให้กรรมการดูได้ว่าจะส่งอะไรออกไป โดยไม่ต้องมีเซิร์ฟเวอร์เมลและไม่ส่งอีเมลจริงไปหาใคร |
| `smtp` | ส่งจริงตามค่า `SMTP_*` ใน `.env` | ตอนต่อกับกล่องจดหมายจริง |

เลือก outbox เป็นค่าเริ่มต้นเพราะ **ตอนสาธิตต้องไม่มีอะไรวิ่งออกอินเทอร์เน็ต**
ถ้าเน็ตในห้องแข่งช้าหรือ SMTP ต้องยืนยันตัวตนเพิ่ม เดโมจะสะดุดโดยไม่จำเป็น
และกติกาข้อ 14 ห้ามใช้ข้อมูลส่วนบุคคลจริง การไม่ส่งออกจริงตอนสาธิตจึงปลอดภัยกว่า

**ข้อความอีเมลอยู่ที่ `TEMPLATES` ใน `services/notification.py` ที่เดียว**
แนวคิดเดียวกับ `StatusPill.tsx` ที่รวม "สถานะ -> ข้อความ" ไว้จุดเดียว
และตั้งใจไม่เล่าโครงสร้าง 4 ขั้นซ้ำในอีเมล เพราะคำอธิบายขั้นตอนอยู่ที่หน้าเว็บ
(`lib/progress.ts`) เขียนซ้ำสองที่แปลว่าวันหนึ่งจะไม่ตรงกัน

**บัญชีที่สมัครด้วยเบอร์โทรอย่างเดียวไม่มีอีเมล** (M1 ให้เลือกได้) ระบบข้ามการส่ง
และบันทึก AuditLog ว่า skipped ไม่ถือเป็นความผิดพลาด ถ้าวันหนึ่งต้องแจ้งกลุ่มนี้
ด้วย ช่องทางที่เหมาะคือ SMS ซึ่งอยู่นอกขอบเขตต้นแบบนี้

### ตั้งค่าส่งจริงผ่าน Gmail (ทำแล้วบนเครื่องทีม)

บัญชีที่ใช้คือ `hotlinedoc.info@gmail.com` ค่าที่ต้องมีใน `backend/.env`

```
EMAIL_BACKEND=smtp
EMAIL_FROM=HoTLinE Doc <hotlinedoc.info@gmail.com>   # ต้องเป็นบัญชีเดียวกับ SMTP_USER
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=hotlinedoc.info@gmail.com
SMTP_PASSWORD=<app password 16 หลัก>
SMTP_STARTTLS=true
```

**รหัสผ่านที่ใช้ล็อกอิน Gmail ตามปกติใช้กับ SMTP ไม่ได้** Google ปิดช่องทาง
"แอปที่มีความปลอดภัยต่ำ" ไปตั้งแต่ปี 2022 ลองยิงจริงแล้วได้
`535 5.7.8 Username and Password not accepted` ต้องเปิด 2-Step Verification
ของบัญชีนั้นก่อน แล้วสร้าง app password ที่ myaccount.google.com/apppasswords
เอา 16 หลักนั้นมาใส่ `SMTP_PASSWORD`

ตรวจว่าตั้งถูกหรือยังโดยไม่ต้องเดินทั้งกระบวนการ

```bash
cd backend && uv run python -m scripts.send_test_email ที่อยู่ปลายทาง@example.com
```

สคริปต์นี้เรียก `send()` ตรง ๆ จึงเห็น error ดิบ ต่างจากของจริงที่รันใน
background task ซึ่งกลืน exception ทุกชนิดโดยตั้งใจ ถ้าไม่มีสคริปต์นี้
ค่าที่ตั้งผิดจะเงียบ เห็นแค่ AuditLog `outcome=failed`

**เทสต์ถูกบังคับให้ใช้ outbox เสมอ** ที่ `backend/tests/conftest.py` เพราะเครื่อง
ที่ตั้ง `EMAIL_BACKEND=smtp` ไว้ใช้งานจริง ถ้าไม่บังคับ การรันเทสต์จะยิงเมล
ไปหาที่อยู่สมมติอย่าง `pytest-officer-owner-xxx@example.com` ทุกครั้งที่เคสไหน
สั่งเจ้าหน้าที่ตัดสินคำขอ ช้า พึ่งเน็ต และทำให้บัญชีผู้ส่งเสียชื่อฟรี ๆ

**จดหมายที่ส่งออกจริงมี `Date` / `Message-ID` / `Auto-Submitted: auto-generated`**
สองตัวแรกกันตัวกรองสแปมหักคะแนน (ผู้ยื่นที่อีเมลตกถังสแปมคือคนที่ค้างอยู่เฉย ๆ
ซึ่งเป็นปัญหาเดิมที่ฟีเจอร์นี้ตั้งใจแก้) ตัวที่สามบอกปลายทางตาม RFC 3834 ว่า
เครื่องเป็นคนส่ง อย่าตอบกลับอัตโนมัติวนมา

### โหมดทดสอบ: ดึงอีเมลทุกฉบับมาเข้ากล่องเดียว (`EMAIL_REDIRECT_TO`)

บัญชีผู้ยื่นที่ใช้ทดสอบเป็นข้อมูลจำลอง อีเมลลงท้าย `@example.com` ซึ่งไม่มีใคร
เปิดอ่านได้ พอเปลี่ยนมาส่งจริงจึงไม่มีทางเห็นว่าจดหมายหน้าตาอย่างไรในกล่องจริง
ตั้ง `EMAIL_REDIRECT_TO=<ที่อยู่ของคุณ>` ใน `backend/.env` แล้วอีเมลถึงผู้ยื่น
**ทุกฉบับ** จะถูกส่งมาที่นั่นแทน หัวข้อขึ้นต้นด้วย `[ทดสอบ]` และบรรทัดแรก
ของเนื้อความบอกว่าฉบับนี้ควรถึงใคร ไม่งั้นทดสอบหลายคำขอแล้วแยกไม่ออก

**ไม่ฝังที่อยู่ไว้ในโค้ด** แม้จะสั้นกว่า เพราะโค้ดขึ้น git (กติกาข้อ 7 ห้าม
ข้อมูลส่วนบุคคลจริง) และการฝังไว้แปลว่าวันสาธิตเมลจะยังเด้งไปหาคนเดิม
โดยไม่มีใครทันสังเกต — ค่าใน `.env` ลบทีเดียวจบและไม่ขึ้น git

**AuditLog ต้องไม่โกหก** ตอนเปิดโหมดนี้ `detail` ต่อท้ายว่า
"(โหมดทดสอบ เปลี่ยนปลายทางไม่ได้ส่งถึงผู้ยื่น)" เพราะ M9 ให้ย้อนดูได้ว่าแจ้ง
ผู้ยื่นไปแล้วจริงหรือไม่ ถ้าบันทึกว่า success เฉย ๆ ทั้งที่จดหมายไปเข้ากล่องคนทดสอบ
ร่องรอยนั้นจะพาคนอ่านเข้าใจผิด

`tests/conftest.py` บังคับปิดโหมดนี้ทุกเคส (คู่กับบังคับ `EMAIL_BACKEND=outbox`)
ไม่งั้นเคสที่ตรวจว่า "ส่งถึงผู้ยื่นคนนั้นจริงไหม" จะล้มบนเครื่องที่เปิดโหมดนี้ค้างไว้

## 16. เจ้าหน้าที่ต้องเห็น "หนังสือที่ลงลายมือชื่อแล้ว" ไม่ใช่ไฟล์ลายเซ็น

ปัญหาที่พบ: แบบฟอร์มที่ระบบกรอกให้ (A01 หนังสือแจ้งฯ / A06 ร.ร.1) เก็บลายมือชื่อ
เป็นไฟล์แนบของเอกสารฉบับนั้น (ดูข้อ 12) ไฟล์เดียวที่ผูกกับเอกสารจึงเป็น
`ลายมือชื่อ.png` พอถึงหน้าตรวจของเจ้าหน้าที่ สิ่งที่เปิดดูได้จึงมีแค่รูปลายเซ็น
ลอย ๆ ซึ่งบอกไม่ได้ว่าเซ็นกำกับข้อความอะไร ทั้งที่คนคนนั้นคือคนที่ต้องกด
"ผ่าน/ไม่ผ่าน" ให้เอกสารฉบับนั้น ฝั่งผู้ยื่นเองก็เห็นไฟล์ชื่อนี้เป็นรายการเอกสาร
จึงเข้าใจได้ว่าสิ่งที่ส่งไปคือรูปลายเซ็น ไม่ใช่หนังสือทั้งใบ

**สิ่งที่ทำ** เพิ่ม `GET /officer/applications/{no}/forms/{code}` คู่กับหน้า
`/officer/applications/[no]/forms/[code]` ที่แสดงกระดาษทั้งใบพร้อมลายมือชื่อ

**กระดาษต้องเป็นใบเดียวกันทั้งสองฝั่ง** การประกอบข้อมูลย้ายไปอยู่ที่
`presenters.to_system_form_out` ที่เดียว และหน้าจอใช้คอมโพเนนต์ตัวเดียวกัน
(`components/common/SystemFormView.tsx` + `SystemFormPaper.tsx` รับ prop `viewer`)
ถ้าปล่อยให้แต่ละฝั่งประกอบเอง วันหนึ่งผู้ยื่นกับเจ้าหน้าที่จะเถียงกันว่าตรวจคนละฉบับ
ซึ่งเป็นบั๊กที่หาสาเหตุยากที่สุดแบบหนึ่ง มีเทสต์ `test_both_sides_read_the_very_same_paper`
เทียบ response สองเส้นทางให้เท่ากันทุกฟิลด์ยกเว้น `can_sign`

**เจ้าหน้าที่อ่านอย่างเดียว** (`can_sign=False` เสมอ) ลายมือชื่อเป็นของผู้ยื่น
เจ้าหน้าที่เซ็นแทนไม่ได้ และไม่มีแผงแก้ชื่อผู้ยื่นในมุมมองนี้

**หน้าผู้ยื่นเลิกแสดง `ลายมือชื่อ.png` เป็นรายการไฟล์** เปลี่ยนเป็นปุ่มเดียวที่พาไป
หนังสือทั้งใบ พร้อมข้อความว่าลงลายมือชื่อแล้ว (และรุ่นที่เท่าไรถ้าเซ็นใหม่)
ไฟล์ยังอยู่ครบในฐานข้อมูลและยังเก็บเป็นรุ่นเหมือนเดิม เปลี่ยนแค่สิ่งที่หน้าจอสื่อ

endpoint ใหม่ใช้ `_load_in_scope` ตัวเดียวกับหน้าอื่นของเจ้าหน้าที่ การเปิดกระดาษ
ของคำขอนอกเขตจึงถูกปฏิเสธและถูกบันทึกลง AuditLog ด้วย (T-09)

### เอกสารที่ออกให้ก็ใช้หลักเดียวกัน

ปัญหาเดียวกันเกิดกับใบอนุญาต/หนังสือรับรอง เจ้าหน้าที่เป็นคนลงนามออกเอกสาร
แต่หลังกดออกแล้วเห็นเพียง "ออกเอกสารแล้ว เลขที่ ..." บนหน้าคำขอ เปิดดูใบจริงไม่ได้
ทั้งที่เป็นคนลงนามเอง เป็นคนที่ผู้ยื่นจะโทรมาถามเมื่อข้อความบนเอกสารผิด
และบางครั้งต้องพิมพ์ส่งมอบให้ผู้มาติดต่อที่เคาน์เตอร์

เพิ่ม `GET /officer/applications/{no}/license` และ `.../license/signature`
คู่กับหน้า `/officer/applications/[no]/license` ปุ่มเข้าหน้านี้อยู่ในกล่อง
"ออกเอกสารแล้ว" บนหน้าคำขอ จึงโผล่เฉพาะเมื่อมีเอกสารให้เปิดจริง ๆ

การประกอบข้อมูลรวมไว้ที่ `presenters.to_license_out_for` และหน้าจอใช้
`components/common/LicenseView.tsx` ตัวเดียวกัน (prop `viewer`) ด้วยเหตุผลเดียวกับ
แบบฟอร์ม เทสต์ `test_officer_and_operator_see_the_same_document` เทียบ response
สองเส้นทางให้เท่ากันทุกฟิลด์

**ปุ่มขึ้นเมื่อ "ออกเอกสารแล้ว" ไม่ใช่เมื่อ "อนุมัติแล้ว"** เพราะอนุมัติกับออกเอกสาร
เป็นคนละขั้นโดยตั้งใจ (M10) ช่วงที่อนุมัติแล้วแต่ยังไม่ลงนาม ยังไม่มีเอกสารให้เปิด
หน้าจอช่วงนั้นจึงแสดงแผงลงนามแทน และ API ตอบ 404 พร้อมบอกว่าต้องลงนามออกเอกสารก่อน

## 17. แผนที่ของจุดติดต่อ เก็บเป็นลิงก์ในฐานข้อมูล

M4 บังคับให้บอกว่า "ต้องไปติดต่อหน่วยงานใด ที่ท้องถิ่นใด" เดิมหน้าจอบอกชื่อ
สำนักงานกับเวลาทำการ ซึ่งพอสำหรับคนที่รู้จักที่นั่นอยู่แล้ว แต่ผู้ประกอบการที่
ไม่เคยไปต้องเอาชื่อไปค้นเองแล้วเดาว่าหมุดไหนใช่ — เป็นจุดที่ไปผิดที่ได้ง่ายที่สุด
ทั้งที่ระบบรู้อยู่แล้วว่าต้องไปที่ไหน

**เก็บเป็นลิงก์ ไม่ใช่พิกัด** `local_authority.map_url` และ `contact_point.map_url`
(migration `c4a91d5e77b2`) เพราะสิ่งที่ผู้ใช้ต้องการคือกดแล้วเปิดแอปแผนที่นำทางได้เลย
และ Super Admin แก้เองได้โดยไม่ต้องรู้พิกัด (US-09) ถ้าเก็บ lat/lng ระบบต้องมี
หน้าจอเลือกหมุดและโค้ดประกอบลิงก์เอง ซึ่งเกินสิ่งที่โจทย์ขอ

**ค่าตั้งต้นใช้รูปแบบ `place_id`** (`app/seeds/local_authorities.py`) เพราะหมุดไม่
เลื่อนตามการแก้ชื่อหรือที่อยู่ และหน้าเว็บใช้รหัสเดียวกันนี้ฝังแผนที่ในหน้าได้ด้วย
ครบทั้ง 19 แห่ง มีเทสต์ `test_every_authority_has_a_map_link` กันไม่ให้ตกหล่น
หมายเหตุ: ไม่พบหมุดของ*เทศบาลตำบล*เทพกระษัตรีแยกต่างหาก จึงใช้หมุดเดียวกับ
อบต.เทพกระษัตรีไปก่อน และบันทึกไว้ในคอมเมนต์ของ seed ว่ายังไม่ได้ยืนยัน

**ฝังแผนที่โดยไม่ใช้ API key** Maps Embed API ทางการต้องมี key ที่ผูกบัญชีคิดเงิน
และต้องเก็บเป็นความลับ ซึ่งเกินขอบเขตต้นแบบ จึงฝังผ่านปลายทางเดียวกับที่ Google
พาไปเองเมื่อเปิดลิงก์แบบ `?output=embed` (ตรวจแล้วตอบ 200 และไม่ตั้ง X-Frame-Options)
เพราะเป็นทางที่ไม่มีเอกสารรับรอง **ทุกจุดที่ฝังแผนที่จึงต้องมีลิงก์ออก Google Maps
คู่กันเสมอ** ถ้าวันสาธิตเน็ตช้าหรือ Google เปลี่ยนปลายทาง ผู้ใช้ยังกดนำทางได้อยู่
โค้ดแปลงลิงก์เป็น URL สำหรับฝังอยู่ที่ `frontend/src/lib/maps.ts` ที่เดียว
ลิงก์รูปแบบอื่นที่ไม่มี `place_id` จะไม่มีปุ่ม "ดูแผนที่" แต่ยังกดเปิดได้ตามปกติ

**แผนที่ถูกซ่อนไว้ก่อน โหลดเมื่อกดเท่านั้น** หน้าคำขอหนึ่งหน้ามีเอกสารหลายฉบับ
ที่มีจุดติดต่อ ถ้าฝัง iframe ทุกอันตั้งแต่เปิดหน้า หน้าจะอืดและยิงออกอินเทอร์เน็ต
โดยที่ผู้ใช้ไม่ได้ขอ

## 18. หน้า "บัญชีของฉัน" หน้าเดียวใช้ทุกบทบาท

เดิมข้อมูลที่กรอกตอนสมัครแก้ไม่ได้เลย คนพิมพ์ชื่อผิดหรือเปลี่ยนเบอร์โทรต้องให้คน
ที่เข้าถึงฐานข้อมูลแก้ให้ ซึ่งเป็นภาระแบบเดียวกับที่โจทย์อยากลด และเบอร์โทรกับอีเมล
ยังเป็นกุญแจเข้าสู่ระบบ (M1) การแก้ไม่ได้จึงแปลว่าเปลี่ยนเบอร์แล้วเข้าระบบไม่ได้อีก

`/account` อยู่ในกลุ่มเส้นทางของตัวเอง (`app/(account)/`) เพราะทุกบทบาทใช้หน้าเดียวกัน
ถ้าวางไว้ใต้ `(operator)` เจ้าหน้าที่กับส่วนกลางจะเข้าไม่ถึง และถ้าทำสี่หน้าแยกตาม
บทบาทก็ต้องแก้สี่ที่ทุกครั้ง เมนูด้านข้างยังเปลี่ยนตามบทบาทเหมือนเดิมเพราะใช้ AppShell ร่วมกัน

**แก้ได้เฉพาะสิ่งที่เป็นของเจ้าของบัญชีเอง** ชื่อ อีเมล เบอร์โทรศัพท์ และรหัสผ่าน
ทุก endpoint ทำงานกับ "เจ้าของโทเคน" เสมอ ไม่มีที่ไหนรับ id ของผู้ใช้เป็นพารามิเตอร์
จึงไม่มีทางส่งคำขอไปแก้ข้อมูลของคนอื่น

| แก้ไม่ได้ | เหตุผล |
|---|---|
| เลขประจำตัวประชาชน | หนึ่งเลขบัตรต่อหนึ่งบัญชีคือกลไกกันบัญชีขยะที่เหลืออยู่หลังตัดสินใจไม่ทำ OTP (ข้อ 3) ถ้าแก้เองได้ กลไกนั้นหมดความหมายทันที |
| บทบาท | ถ้าเจ้าของบัญชีเปลี่ยนเองได้ ใครก็เลื่อนตัวเองเป็นเจ้าหน้าที่แล้วเปิดคำขอของคนอื่นได้ |
| ชื่อผู้ยื่นบนแบบฟอร์ม | เป็นคนละอย่างกับชื่อเจ้าของบัญชี (`operator.display_name`) และถูกล็อกหลังยื่นคำขอแล้ว จึงยังแก้ที่หน้าแบบฟอร์มของคำขอนั้นเหมือนเดิม |

ทั้งสองอย่างที่แก้ไม่ได้ยัง**แสดงไว้บนหน้าจอพร้อมเหตุผล** ไม่ได้ซ่อนทิ้ง เพราะผู้ใช้
ควรเห็นว่าระบบเก็บอะไรของเขาไว้บ้าง ไม่ใช่เห็นเฉพาะช่องที่กรอกได้ (โจทย์ข้อ 8
เรื่องการดูแลข้อมูลส่วนบุคคล) เลขบัตรแสดงแบบปิดบังเท่านั้นตามกฎเดิมของระบบ

**เปลี่ยนรหัสผ่านต้องกรอกรหัสเดิมเสมอ** ไม่งั้นโทเคนที่ถูกขโมยไปจะยึดบัญชีได้ทันที
และการกรอกรหัสเดิมผิดถูกบันทึกลง AuditLog (`password.change` outcome=denied)
เพราะเป็น "ความพยายามเข้าถึง" แบบเดียวกับการล็อกอินไม่สำเร็จและ T-09
**ข้อจำกัดที่รู้อยู่:** โทเคนที่ออกไปก่อนเปลี่ยนรหัสยังใช้ได้ต่อ เพราะต้นแบบนี้
ไม่มีที่เก็บรายการโทเคน (JWT ไร้สถานะ) ระบบจริงต้องถอนโทเคนทั้งหมดเมื่อเปลี่ยนรหัส

**AuditLog บันทึกว่าแก้ "ช่องไหน" ไม่ใช่ "แก้เป็นอะไร"** อีเมลและเบอร์โทรเป็นข้อมูล
ส่วนบุคคล ไม่ควรไปกองอยู่ในตารางที่คนอื่นเปิดอ่านได้ หลักเดียวกับที่ห้ามเขียน
เลขบัตรเต็มลง log และที่อีเมลแจ้งเตือนไม่เขียนที่อยู่ผู้รับลง detail (ข้อ 15)

**กฎการตรวจใช้ชุดเดียวกับตอนสมัคร** ย้ายมาเป็นฟังก์ชันใน `schemas/auth.py`
(`clean_email` / `clean_phone` / `clean_person_name` / `check_password_length`)
ถ้าเขียนซ้ำสองที่ วันหนึ่งกฎจะไม่ตรงกัน แล้วข้อมูลที่แก้ทีหลังจะหลุดกฎที่ตอนสมัครกันไว้
