# บันทึกการตัดสินใจ (Decision Log)

สรุปสิ่งที่ตกลงกันไว้ก่อนเริ่มเขียนโค้ด พร้อมเหตุผล — เพื่อให้ทุกคนในทีม
(และตัวเราเองตอนเหนื่อยชั่วโมงที่ 10) ไม่ต้องถกเรื่องเดิมซ้ำ

---

## 1. เทคโนโลยี: Next.js + FastAPI + PostgreSQL

โจทย์ข้อ 10 ระบุชื่อทั้งสามตัวไว้ตรง ๆ ในรายการที่อนุญาต จึงไม่ต้องขออนุญาตเพิ่ม

**ข้อได้เปรียบที่ตั้งใจใช้:** FastAPI สร้าง OpenAPI + Swagger UI ที่ `/docs` ให้อัตโนมัติจาก
Pydantic models → ได้ deliverable ข้อ "เอกสาร API พร้อมตัวอย่าง request/response" แทบไม่ต้องลงแรง
และเปิดหน้านี้โชว์กรรมการตอนนำเสนอได้เลย

**ข้อควรระวัง:** อย่าเขียน business logic ใน Next.js API routes เพราะโจทย์ให้คะแนนการแยก FE/BE
ชัดเจน ถ้ากฎจำแนกประเภทไปโผล่ฝั่ง Next.js กรรมการจะถามว่าตกลงใครเป็น backend

## 2. ไม่ใช้ Docker

เดิมตั้งใจใช้ Docker Compose แต่เปลี่ยนเมื่อรู้ว่าทีมใช้เครื่องเดียว —
**ประโยชน์หลักของ Docker คือทำให้ทุกเครื่องเหมือนกัน ซึ่งไม่มีความหมายเมื่อมีเครื่องเดียว**
เหลือแต่ต้นทุน: กิน RAM, ต้องดาวน์โหลดหลาย GB, rebuild ทุกครั้งที่แก้ dependency

ตอนนี้ย้ายมา WSL ที่มี PostgreSQL 14 รันอยู่แล้ว ยิ่งไม่จำเป็น

## 3. Python 3.13 ผ่าน uv (ไม่ใช้ python3 ของระบบ)

Ubuntu 22.04 มาพร้อม Python 3.10 ซึ่งไม่มี `StrEnum` (3.11+) และ `datetime.UTC` (3.11+)
ทางเลือกคือเขียนโค้ดให้เข้ากับ 3.10 หรือดึง 3.13 มาแยก — เลือกอย่างหลัง เพราะ `uv python install`
ใช้เวลาไม่กี่วินาที ไม่ต้อง sudo และไม่กระทบ `python3` ของระบบที่ใช้กับงานอื่นอยู่

## 4. Node 24 ผ่าน nvm

เครื่องตั้ง nvm default ไว้ที่ Node 12 และ shell ปกติได้ Node 16 — ทั้งคู่รัน Next.js 16 ไม่ได้
โชคดีที่มี Node 24.14.1 ติดตั้งไว้อยู่แล้ว จึงเพิ่ม `.nvmrc` ระบุ `24` ให้ทุกคนใช้เวอร์ชันเดียวกัน

## 5. วิธีทำงาน 3 คน 1 คีย์บอร์ด

โจทย์มี deliverable 6 ชิ้น แต่**มีแค่ชิ้นที่ 4 (Working Software) ที่ต้องใช้เครื่อง**
อีก 5 ชิ้นทำบนกระดาษได้ (โจทย์ระบุเองว่า wireframe "จะเป็นภาพร่างหรือไฟล์ออกแบบก็ได้")

| ตำแหน่ง | ทำอะไร |
|---|---|
| Driver | จับคีย์บอร์ด เขียนโค้ด |
| Navigator | อ่านโจทย์เทียบ จับ bug เปิด Swagger เช็ก API ไล่ test case |
| Scribe | เอกสาร: requirement, use case, ER, wireframe, test case, สไลด์ |

**สลับทุก 90 นาที** → ทุกคนได้ drive จริง ได้ทำเอกสารจริง และอธิบายส่วนที่ตัวเองรับผิดชอบได้
ตอนนำเสนอ ซึ่งเป็นเกณฑ์ข้อ 4 (20 คะแนน) ตรง ๆ

ผลพลอยได้: pair programming ทำให้ไม่มี merge conflict เลย ซึ่งทีมที่ใช้ 3 เครื่องมักเสียเวลา 1–2 ชม.

## 6. Git: ระบุ author ตามคนที่ drive

ถ้า commit ปกติ ทุก commit จะขึ้นชื่อเจ้าของเครื่องคนเดียว กรรมการเปิด repo แล้วจะเห็นว่า
มีคนทำคนเดียว → เสียคะแนนข้อ "สมาชิกทุกคนมีส่วนร่วมในการพัฒนา" ทั้งที่ทุกคนทำจริง

แก้ด้วย `./scripts/git-setup.sh` ที่สร้าง alias:

```bash
git ca a -m "feat: ..."   # commit ในชื่อสมาชิก A
git who                   # ดูว่าแต่ละคน commit ไปกี่ครั้ง
```

เปิด `git who` หรือหน้า Contributors บน GitHub โชว์กรรมการได้ตอนนำเสนอ

## 7. ระบบดีไซน์

ค่าสีดึงจากไฟล์โลโก้จริง ไม่ได้กะเอาจากภาพ:

| | Hex | ใช้ที่ |
|---|---|---|
| Teal | `#009494` | ปุ่มหลัก, active, แบรนด์ |
| Teal สว่าง | `#00A6A6` | hover |
| Navy | `#0D2344` | ตัวอักษรหลัก, เส้นขอบ |
| Mint | `#C8EDE2` | พื้นอ่อน, badge |

**ลายเซ็นของสไตล์นี้ที่ต้องไม่ทำหาย** (ดูตัวอย่างใน `docs/reference-ui/`):

1. **หัวข้อเป็นคำถามที่พูดกับผู้ใช้** — "ที่พักของคุณต้องดำเนินการอะไร?" ไม่ใช่ "แบบฟอร์มประเมินประเภทที่พัก"
2. **ทุกหัวข้อมีคำอธิบายสั้นใต้ชื่อเสมอ** ไม่มี label ลอย
3. **รหัสเอกสารนำหน้าเสมอ** — A01–A08 (ทำเองได้) / B01–B07 (ต้องขอจากหน่วยงานอื่น)
4. **Layout 2 คอลัมน์ 60/40** — ซ้าย = สิ่งที่ต้องทำ, ขวา = บริบท/ผลลัพธ์/ความช่วยเหลือ
5. **Badge "ต้นแบบ • ข้อมูลจำลอง" ข้างโลโก้** + footer disclaimer — ตอบกติกาข้อห้ามใช้ข้อมูลจริงไปในตัว
6. ภาพประกอบลายเส้นและข้อความลายมือมุมล่างซ้าย

## 8. มาสคอต — แมปท่าทางกับสถานะ ไม่ใช่เลือกตามความสวย

| ท่า | ใช้ที่ |
|---|---|
| `wave` | หน้าแรก, ต้อนรับหลังสมัคร, empty state ทั่วไป |
| `upload` | dropzone ว่าง, ระหว่างอัปโหลด (M5) |
| `inspect` | AI ช่วยตรวจ (S1), เจ้าหน้าที่กำลังตรวจ (M8), ผลค้นหาว่าง |
| `waiting` | รอดำเนินการ, "อยู่ในขั้นนี้ N วัน" (M7), คำขอค้าง |
| `success` | ยื่นสำเร็จ (M6), อนุมัติ, ใบอนุญาต (M10) |
| `support` | ช่วยเหลือ, FAQ, กระดานสนทนา (C1), หน้า error |

**หลักที่ถือไว้: อย่าให้มาสคอตยิ้มร่าเริงตอนบอกข่าวร้าย** — ตอนแจ้ง "ไม่ผ่าน" ให้ใช้ไอคอนธรรมดา
จะดูน่าเชื่อถือกว่า และมาสคอตต้องไม่เป็นตัวสื่อความหมายเพียงลำพัง ต้องมีข้อความกำกับเสมอ (NFR Accessibility)

**ท่าที่ยังขาดและควรเจนเพิ่ม:** ท่า "เอกสารขอให้แก้ไข" (เอียงคอ ทำหน้างง ไม่ใช่หน้าเศร้า)
สำหรับ T-08 ซึ่งเป็น flow ที่ต้องเดโมแน่นอน

## 12. ลายมือชื่อในแบบฟอร์ม และการออกเป็น PDF

ระบบมีแบบฟอร์มที่กรอกให้เองได้ทั้งฉบับสองแบบ แยกตามผลจำแนกประเภท:
**A01 แบบหนังสือแจ้งสถานที่พักที่ไม่เป็นโรงแรม** (เส้นไม่เข้าข่ายโรงแรม) และ
**A06 แบบ ร.ร.1 คำขอรับใบอนุญาตประกอบธุรกิจโรงแรม** (ประเภทที่ 1 และ 2)
ทั้งคู่ระบบกรอกให้ได้หมดยกเว้นสิ่งเดียวคือ **ลายมือชื่อผู้ยื่น** ซึ่งเป็นสิ่งที่
ทำให้เอกสารฉบับนั้นมีผล จึงต้องมีทั้งช่องให้ลงลายมือชื่อในระบบ และทางออกเป็นไฟล์
ที่พิมพ์/ส่งต่อได้

ทั้งสองฉบับใช้ endpoint เดียว (`GET /applications/{no}/forms/{code}`) service เดียว
(`services/system_form.py`) และโครงกระดาษเดียว (`SystemFormPaper.tsx`) ต่างกันแค่
เนื้อความตรงกลาง ถ้าทำเป็นสองชุดคู่ขนาน สองชุดนั้นจะค่อย ๆ เพี้ยนจากกัน
แบบเดียวกับที่ `api/presenters.py` มีไว้กันไม่ให้ /wizard กับ /applications เพี้ยนกัน

**PDF: ใช้การพิมพ์ของเบราว์เซอร์ ไม่สร้างไฟล์ฝั่งเซิร์ฟเวอร์**
เหตุผลเดียวกับใบอนุญาต (M10) — หน้าต่างพิมพ์ของทุกเบราว์เซอร์มีปลายทาง
"บันทึกเป็น PDF" อยู่แล้ว การเพิ่มไลบรารี PDF ฝั่ง Python แลกมาด้วยปัญหา
ฟอนต์ไทย (สระบนล่างเพี้ยน ต้องฝังไฟล์ฟอนต์เอง) ซึ่งกินเวลามากเกินกว่าที่มี
และได้ผลลัพธ์ที่แย่กว่า หน้าเว็บจึงเป็นทั้งหน้าจอและต้นฉบับกระดาษในตัวเดียวกัน

**ลายมือชื่อเก็บเป็นไฟล์แนบของ A01 ไม่ใช่คอลัมน์ใหม่**
ทางเลือกคือเพิ่ม `signature_path` ใน `application` หรือใช้กลไกเอกสารที่มีอยู่
เลือกอย่างหลัง เพราะได้มาฟรีทั้งชุด: เซ็นใหม่กลายเป็นรุ่นถัดไปโดยไม่ทับของเดิม
(ข้อ 8 ของโจทย์) เจ้าหน้าที่ตรวจและขอให้แก้ไขได้เหมือนเอกสารฉบับอื่น
และล็อกอัตโนมัติเมื่อยื่นคำขอแล้ว โดยไม่ต้องเขียนกฎเพิ่มสักบรรทัด

**ต้องลงลายมือชื่อก่อนจึงจะยื่นได้ (มติทีม)**
แบบฟอร์มในระบบไม่ถูกยกเว้นใน `missing_mandatory` อีกต่อไป เพราะลายมือชื่อคือ
สิ่งที่ทำให้หนังสือแจ้งมีผล การปล่อยให้ยื่นหนังสือที่ไม่มีลายมือชื่อได้เท่ากับ
ระบบยอมรับเอกสารที่ใช้ไม่ได้จริง ผลที่ตามมาสามอย่างซึ่งตั้งใจให้สอดคล้องกัน:

1. `missing_mandatory` นับแบบฟอร์มที่ยังไม่เซ็นเป็นเอกสารที่ขาด และติดธง
   `needs_signature` มาด้วย เพื่อให้ข้อความบอกว่า "ยังไม่ได้ลงลายมือชื่อ"
   ไม่ใช่ "ยังไม่ได้แนบไฟล์" ซึ่งจะพาผู้ใช้ไปหาไฟล์มาแนบผิด ๆ
2. สถานะของแบบฟอร์มที่ยังไม่เซ็นเป็น "ยังไม่ได้อัปโหลด" ไม่ใช่ "อัปโหลดแล้ว"
   ไม่งั้นสถานะจะขัดกับปุ่มยื่นที่กดไม่ได้ และผู้ใช้จะหาไม่เจอว่าติดตรงไหน
3. ลายมือชื่อถูกนับใน `pending_documents` ของเจ้าหน้าที่ด้วย ไม่งั้นมันจะเป็น
   สิ่งเดียวในคำขอที่ไม่มีใครตรวจ

ผู้ที่ถนัดเซ็นบนกระดาษยังทำได้เหมือนเดิม — พิมพ์แบบฟอร์มออกไปเซ็น ถ่ายรูป
แล้วอัปโหลดรูปนั้นกลับเข้ามา ระบบจึงไม่ได้ปิดทางใคร

**ช่องติ๊กเอกสารแนบในแบบ ร.ร.1 ไม่ได้เก็บเป็นข้อมูล**
แบบ ร.ร.1 มีช่องให้ติ๊กว่าแนบเอกสารใดมาด้วย (A07–A09) ระบบติ๊กให้เองจากว่า
แนบไฟล์แล้วหรือยัง ไม่ได้เพิ่มคอลัมน์ "ติ๊กแล้ว" เพราะนั่นคือข้อมูลชุดเดียวกัน
ที่เก็บซ้ำสองที่ (3NF) และจะเพี้ยนทันทีที่มีคนติ๊กแต่ไม่แนบ หรือแนบแต่ไม่ติ๊ก

**ชื่อผู้ยื่นบนแบบฟอร์มแก้ได้เอง**
แบบ ร.ร.1 มีช่องบุคคลธรรมดา/นิติบุคคล แต่ตอนสมัครระบบตั้งชื่อผู้ประกอบการให้
เท่ากับชื่อ-นามสกุลของผู้สมัครไปก่อน จึงเพิ่ม `PATCH /applications/{no}/applicant`
ให้แก้ได้ตราบที่คำขอยังไม่ถูกยื่น แก้ที่ตาราง `operator` ไม่ใช่ `app_user`
เพราะ "ผู้ประกอบการ" กับ "บัญชีผู้ใช้" เป็นคนละสิ่ง (ดูคอมเมนต์ใน models/property.py)
เลขทะเบียนนิติบุคคลเก็บเป็นตัวเลขล้วน 13 หลักด้วยเหตุผลเดียวกับเบอร์โทร

## 13. ลายมือชื่อผู้ลงนามบนเอกสารที่ระบบออกให้ (M10)

ใบอนุญาตและหนังสือรับรองการแจ้งเดิมมีแต่ชื่อเจ้าหน้าที่เป็นข้อความ ซึ่งยังไม่ใช่
เอกสารที่ลงนามแล้ว ด้วยเหตุผลเดียวกับข้อ 12 จึงให้เจ้าหน้าที่ลงลายมือชื่อ
**ตอนกดออกเอกสาร** และลายมือชื่อนั้นไปปรากฏบนกระดาษที่ผู้ยื่นพิมพ์ออกไป

**การเซ็นคือขั้นตอนเดียวกับการออกเอกสาร ไม่ใช่ขั้นตอนแยก** — ปุ่ม "ออกใบอนุญาต"
กลายเป็นปุ่ม "ลงนามและออกเอกสาร" ใต้ช่องเซ็น ถ้าแยกเป็นสองปุ่มจะเกิดสถานะกลางที่
เอกสารออกไปแล้วแต่ยังไม่มีใครลงนาม ซึ่งเป็นสถานะที่ไม่ควรมีอยู่จริง

**เก็บเป็นไฟล์ ไม่ใช่ document_file** — ตาราง `document_file` ผูกกับ "เอกสารประกอบ
คำขอ" ที่ต้องมี `document_type` และเข้าสู่กระบวนการตรวจของเจ้าหน้าที่
ลายมือชื่อผู้ลงนามเป็นส่วนหนึ่งของเอกสารที่ระบบออก ไม่ใช่ของที่ผู้ยื่นส่งมาให้ตรวจ
จึงเก็บเป็น `license.issuer_signature_path` (migration `5b1e70c4a9d2`)
เก็บเป็น path ไม่ใช่ไบต์ในฐานข้อมูล ด้วยเหตุผลเดียวกับ `document_file.stored_path`

ใบที่ออกไปก่อนหน้านี้ไม่มีลายมือชื่อเก็บไว้ หน้าพิมพ์จึงเว้นเส้นลงชื่อไว้ให้เซ็น
ด้วยปากกา แทนที่จะพังหรือขึ้นรูปว่าง

**ทางเลือกสองทางในการเซ็น** — วาดบนจอ หรืออัปโหลดรูปลายเซ็น — ไม่ใช่ของแถม
แต่จำเป็นตาม NFR Accessibility เพราะผู้ที่ใช้คีย์บอร์ดอย่างเดียววาดด้วยเมาส์ไม่ได้
ทั้งสองทางออกมาเป็น PNG พื้นหลังโปร่งเหมือนกัน เพื่อให้วางทับเส้นลงชื่อได้ไม่บังเส้น
