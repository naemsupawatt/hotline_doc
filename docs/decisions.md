# บันทึกการตัดสินใจ (Decision Log)

สรุปสิ่งที่ตกลงกันไว้ก่อนเริ่มเขียนโค้ด พร้อมเหตุผล — เพื่อให้ทุกคนในทีม
(และตัวเราเองตอนเหนื่อยชั่วโมงที่ 10) ไม่ต้องถกเรื่องเดิมซ้ำ

---

## 1. เทคโนโลยี: Next.js + FastAPI + PostgreSQL

โจทย์ข้อ 10 ระบุชื่อทั้งสามตัวไว้ตรง ๆ ในรายการที่อนุญาต จึงไม่ต้องขออนุญาตเพิ่ม

**ข้อได้เปรียบที่ตั้งใจใช้:** FastAPI สร้าง OpenAPI + Swagger UI ที่ `/docs` ให้อัตโนมัติจาก
Pydantic models → ได้ deliverable ข้อ "เอกสาร API พร้อมตัวอย่าง request/response" แทบไม่ต้องลงแรง
และเปิดหน้านี้โชว์กรรมการตอนนำเสนอได้เลย

**ข้อควรระวัง:** อย่าเขียน business logic ใน Next.js API routes เพราะโจทย์ให้คะแนนการแยก FE/BE
ชัดเจน ถ้ากฎจำแนกประเภทไปโผล่ฝั่ง Next.js กรรมการจะถามว่าตกลงใครเป็น backend

## 2. ไม่ใช้ Docker

เดิมตั้งใจใช้ Docker Compose แต่เปลี่ยนเมื่อรู้ว่าทีมใช้เครื่องเดียว —
**ประโยชน์หลักของ Docker คือทำให้ทุกเครื่องเหมือนกัน ซึ่งไม่มีความหมายเมื่อมีเครื่องเดียว**
เหลือแต่ต้นทุน: กิน RAM, ต้องดาวน์โหลดหลาย GB, rebuild ทุกครั้งที่แก้ dependency

ตอนนี้ย้ายมา WSL ที่มี PostgreSQL 14 รันอยู่แล้ว ยิ่งไม่จำเป็น

## 3. Python 3.13 ผ่าน uv (ไม่ใช้ python3 ของระบบ)

Ubuntu 22.04 มาพร้อม Python 3.10 ซึ่งไม่มี `StrEnum` (3.11+) และ `datetime.UTC` (3.11+)
ทางเลือกคือเขียนโค้ดให้เข้ากับ 3.10 หรือดึง 3.13 มาแยก — เลือกอย่างหลัง เพราะ `uv python install`
ใช้เวลาไม่กี่วินาที ไม่ต้อง sudo และไม่กระทบ `python3` ของระบบที่ใช้กับงานอื่นอยู่

## 4. Node 24 ผ่าน nvm

เครื่องตั้ง nvm default ไว้ที่ Node 12 และ shell ปกติได้ Node 16 — ทั้งคู่รัน Next.js 16 ไม่ได้
โชคดีที่มี Node 24.14.1 ติดตั้งไว้อยู่แล้ว จึงเพิ่ม `.nvmrc` ระบุ `24` ให้ทุกคนใช้เวอร์ชันเดียวกัน

## 5. วิธีทำงาน 3 คน 1 คีย์บอร์ด

โจทย์มี deliverable 6 ชิ้น แต่**มีแค่ชิ้นที่ 4 (Working Software) ที่ต้องใช้เครื่อง**
อีก 5 ชิ้นทำบนกระดาษได้ (โจทย์ระบุเองว่า wireframe "จะเป็นภาพร่างหรือไฟล์ออกแบบก็ได้")

| ตำแหน่ง | ทำอะไร |
|---|---|
| Driver | จับคีย์บอร์ด เขียนโค้ด |
| Navigator | อ่านโจทย์เทียบ จับ bug เปิด Swagger เช็ก API ไล่ test case |
| Scribe | เอกสาร: requirement, use case, ER, wireframe, test case, สไลด์ |

**สลับทุก 90 นาที** → ทุกคนได้ drive จริง ได้ทำเอกสารจริง และอธิบายส่วนที่ตัวเองรับผิดชอบได้
ตอนนำเสนอ ซึ่งเป็นเกณฑ์ข้อ 4 (20 คะแนน) ตรง ๆ

ผลพลอยได้: pair programming ทำให้ไม่มี merge conflict เลย ซึ่งทีมที่ใช้ 3 เครื่องมักเสียเวลา 1–2 ชม.

## 6. Git: ระบุ author ตามคนที่ drive

ถ้า commit ปกติ ทุก commit จะขึ้นชื่อเจ้าของเครื่องคนเดียว กรรมการเปิด repo แล้วจะเห็นว่า
มีคนทำคนเดียว → เสียคะแนนข้อ "สมาชิกทุกคนมีส่วนร่วมในการพัฒนา" ทั้งที่ทุกคนทำจริง

แก้ด้วย `./scripts/git-setup.sh` ที่สร้าง alias:

```bash
git ca a -m "feat: ..."   # commit ในชื่อสมาชิก A
git who                   # ดูว่าแต่ละคน commit ไปกี่ครั้ง
```

เปิด `git who` หรือหน้า Contributors บน GitHub โชว์กรรมการได้ตอนนำเสนอ

## 7. ระบบดีไซน์

ค่าสีดึงจากไฟล์โลโก้จริง ไม่ได้กะเอาจากภาพ:

| | Hex | ใช้ที่ |
|---|---|---|
| Teal | `#009494` | ปุ่มหลัก, active, แบรนด์ |
| Teal สว่าง | `#00A6A6` | hover |
| Navy | `#0D2344` | ตัวอักษรหลัก, เส้นขอบ |
| Mint | `#C8EDE2` | พื้นอ่อน, badge |

**ลายเซ็นของสไตล์นี้ที่ต้องไม่ทำหาย** (ดูตัวอย่างใน `docs/reference-ui/`):

1. **หัวข้อเป็นคำถามที่พูดกับผู้ใช้** — "ที่พักของคุณต้องดำเนินการอะไร?" ไม่ใช่ "แบบฟอร์มประเมินประเภทที่พัก"
2. **ทุกหัวข้อมีคำอธิบายสั้นใต้ชื่อเสมอ** ไม่มี label ลอย
3. **รหัสเอกสารนำหน้าเสมอ** — A01–A08 (ทำเองได้) / B01–B07 (ต้องขอจากหน่วยงานอื่น)
4. **Layout 2 คอลัมน์ 60/40** — ซ้าย = สิ่งที่ต้องทำ, ขวา = บริบท/ผลลัพธ์/ความช่วยเหลือ
5. **Badge "ต้นแบบ • ข้อมูลจำลอง" ข้างโลโก้** + footer disclaimer — ตอบกติกาข้อห้ามใช้ข้อมูลจริงไปในตัว
6. ภาพประกอบลายเส้นและข้อความลายมือมุมล่างซ้าย

## 8. มาสคอต — แมปท่าทางกับสถานะ ไม่ใช่เลือกตามความสวย

| ท่า | ใช้ที่ |
|---|---|
| `wave` | หน้าแรก, ต้อนรับหลังสมัคร, empty state ทั่วไป |
| `upload` | dropzone ว่าง, ระหว่างอัปโหลด (M5) |
| `inspect` | AI ช่วยตรวจ (S1), เจ้าหน้าที่กำลังตรวจ (M8), ผลค้นหาว่าง |
| `waiting` | รอดำเนินการ, "อยู่ในขั้นนี้ N วัน" (M7), คำขอค้าง |
| `success` | ยื่นสำเร็จ (M6), อนุมัติ, ใบอนุญาต (M10) |
| `support` | ช่วยเหลือ, FAQ, กระดานสนทนา (C1), หน้า error |

**หลักที่ถือไว้: อย่าให้มาสคอตยิ้มร่าเริงตอนบอกข่าวร้าย** — ตอนแจ้ง "ไม่ผ่าน" ให้ใช้ไอคอนธรรมดา
จะดูน่าเชื่อถือกว่า และมาสคอตต้องไม่เป็นตัวสื่อความหมายเพียงลำพัง ต้องมีข้อความกำกับเสมอ (NFR Accessibility)

**ท่าที่ยังขาดและควรเจนเพิ่ม:** ท่า "เอกสารขอให้แก้ไข" (เอียงคอ ทำหน้างง ไม่ใช่หน้าเศร้า)
สำหรับ T-08 ซึ่งเป็น flow ที่ต้องเดโมแน่นอน

## 9. สิ่งที่ยังไม่มีในมู้ดบอร์ดและต้องออกแบบเพิ่ม

มู้ดบอร์ด 8 ภาพครอบคลุม Must Have ไป 9 จาก 11 ข้อ ที่ยังขาด:

- **M1** หน้าสมัคร/เข้าสู่ระบบ + ยืนยันตัวตน
- **M10** หน้าใบอนุญาตอิเล็กทรอนิกส์ที่พิมพ์ได้
- **M8 (ส่วนแรก)** หน้าคิวคำขอของเจ้าหน้าที่ (ในภาพมีแค่หน้า detail)
- **US-09** หน้า Super Admin แก้ค่าธรรมเนียม/กฎจำแนก — ทำสวยไม่ต้องมาก แต่**ต้องมี**
- หน้าปักหมุดพิกัดบนแผนที่
- **Mobile layout** — ทุกภาพเป็น desktop ล้วน แต่ NFR บังคับว่าต้องใช้บนจอเล็กได้จริง
  และ US-04 คือถ่ายรูปจากมือถือ → **หน้าอัปโหลดต้องมี mobile view อย่างน้อย 1 หน้าไว้เดโม**

## 11. ความเสี่ยง: เครื่องเดียว = จุดพังจุดเดียว

ถ้าเครื่องนี้มีปัญหา ทีมจบทันที ไม่มี "เดี๋ยวใช้เครื่องฉันแทน" จึงต้อง:

1. `git push` ทุกครั้งที่สลับตำแหน่ง (ทุก 90 นาที)
2. `pg_dump` ลงไฟล์ใน repo ตอนจบวันที่ 1 แล้ว commit ไปด้วย
3. อัดวิดีโอเดโม**เช้าวันที่ 2** ไม่ใช่นาทีสุดท้าย
4. ปิด auto-update / sleep ของเครื่องก่อนเริ่มงาน
